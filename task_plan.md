## Current Working Rules

- Prefer local executable behavior over autogenerated summaries.
- Use `-h` where supported; note wrapper-specific help/version quirks in `Guardrails`.
- Keep descriptions focused on trigger conditions, not workflow summaries.
- Avoid changing generator infrastructure unless a real defect is found.
- When a CLI's short option collides with help (for example `RNAsnoop -h`), capture the real help invocation explicitly in `Guardrails`.
- Preserve executable-name quirks when the skill name and binary casing differ (for example `rnapkplex` vs `RNAPKplex`).
- Where local man pages and live binaries disagree, prefer live executable behavior and document the discrepancy in `Guardrails`.
- If a binary cannot start because of missing shared libraries, use the local man page and binary strings conservatively and call out the environment failure explicitly.
- Daemon-style tools may have skill-folder names that differ from the real executable (`hmmpgmd-shard` skill vs `hmmpgmd_shard` binary); preserve both names when documenting them.
- BLAST VDB tools follow BLAST+ single-dash control flags (`-help`, `-version`) even when autogenerated references guessed GNU-style `--help` / `--version`.
- Legacy samtools helper scripts often have no real help/version interface at all; many treat `--help` or `--version` as filenames or stdin-like payloads instead of metadata switches.
- ViennaRNA tools mostly expose clean `--help` / `--version`, but wrappers or blocked binaries still need verification against the actual local environment before documenting them.
- EDirect archive wrappers are operational scripts, not passive help emitters; `--help` / `--version` frequently enter real setup / download / indexing paths instead of printing safe metadata.
- Tiny EDirect UID-list utilities may look trivial, but autogenerated references can still be wrong about their true set operation; source inspection is cheap and worth doing before documenting them.
- EDirect converter wrappers are often just a single `transmute` or `xtract` call; documenting the real dependency surface (`transmute` / `xtract` must be on `PATH`) is more useful than repeating generic “converts format A to B” text.
- Small VCF/text/GTF helpers often hide important algorithmic assumptions in a few lines of source (for example hard-coded diploid AC/AN recalculation or exon merging within 5 bp), so even “obvious” wrappers still need source inspection.
- GenBank helper wrappers frequently compose each other (`gbf2xml | xml2fsa`, `gbf2xml | xml2tbl`, `gbf2info | xtract`), so documenting the pipeline shape is more informative than treating them as standalone black-box converters.
- Small GFF / interval wrappers frequently have misleading or incomplete argument checks; source-level arity and stdin assumptions are worth verifying before trusting autogenerated usage text.
- EDirect shell helpers that appear runnable by absolute path may still fail quietly unless the full bio / EDirect bin directory is on `PATH`.
- Name-based or score-sounding wrapper names can be deceptive; some tools marketed as "top hits" or accession helpers are actually simple first-column group filters or text tokenizers.
- Some tiny shell wrappers ignore `-h` / `--help` entirely and can exit successfully with no output, so silent success is not evidence of a healthy help path.
- Convenience wrappers around `nquire` may depend on ambient helper functions or sibling scripts that are not present in a plain shell invocation, so a live smoke test is still worth doing even after source inspection.
- One-line `awk` / `sed` wrappers can still hide important contract details such as mandatory single-quote shell escaping, implicit tab-only field splitting, or CSV-like output that does not truly escape data.
- XML-conversion helpers with optional positional files may use that file for a transform table or cached lookup metadata rather than as the primary input stream, so stdin/file roles need to be verified explicitly.
- Some EDirect wrappers repair sibling-tool lookup themselves (`ecollect`), while others assume the full bio / EDirect bin directory is already on `PATH` (`blst2tkns`, `pmc2info`, `pmc2bioc`); that difference needs to be documented explicitly.
- For mixed batches, prioritize short shell / Perl / Python wrappers with exposed source over opaque ELF binaries unless there is a man page or safe runtime help path to anchor the rewrite.
- For legacy compiled tools, it is often safer to combine live `-h` / `-help` / `-version` evidence with conservative `strings` output than to over-interpret binary internals.
