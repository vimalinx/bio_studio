这不是一个普通生信仓库。

Bio Studio 更像一套专门给 AI agent 使用的生物计算工作台。它把操作协议、Claude skills、MCP servers、隔离项目目录、共享参考数据，以及 Evo2 / RFdiffusion / Biomni 这类重型外部引擎，压进同一个可执行研究环境里。人类读 README，AI 读协议后直接干活。

它真正卖的不是某一个模型 而是把“环境、流程、工具、任务现场”收束为一个 AI 可操作的研究面板。
核心资产不只是代码 还包括样例项目、文档规约、经验记录、共享参考和挂载的外部能力。
正确理解方式 把它当作“AI 研究操作系统”，而不是单一应用或整洁的 SDK 仓库。

一句话定性

Bio Studio 的核心价值，在于把 AI 需要的上下文预先编排好了。

你不需要从零教 agent 目录规范、工具入口、项目隔离方式、环境验证规则或常见坑。 这些东西已经被写进文档、脚本、skills 和样例项目里，形成了一层可复用的操作语境。

它不是什么

不是纯应用，不是纯算法仓库，也不是单一模型的外壳。

不是一个整洁 SDK 自研代码相对薄，更多是 wrapper、协议、模板和 orchestration glue。
不是只给人看的文档库 很多内容明显是给 agent 当工作约束和执行上下文用的。
不是单一科研项目 仓库里同时存在环境维护、教学案例、RNA-seq 分析、设计实验和第三方引擎集成。

它更接近什么

更像一个 AI 生物计算 studio runtime。

protocol layer 告诉 agent 在部署工具和跑分析时必须遵守的动作顺序。
workspace layer 把真实任务放进项目隔离目录，避免环境和产物相互污染。
engine layer 通过 vendored repos 和 MCP，让 AI 直接碰到外部模型与数据库。
仓库地图

六层结构，决定了这个仓库为什么看起来不像“标准项目”。

如果把所有目录平铺看，它会显得很散。把它拆成六层后，角色就清晰了： 规则、骨架、接口、任务现场、外挂引擎、共享与遗留。

`projects/` 才是 agent 实际工作的地方。每个项目都有自己独立的数据、脚本、日志和结果。 环境验证、RNA-seq 分析、toy design playground、酵母学习项目都放在这里。

projects/test_env_validation projects/ai_design_playground projects/test_rnaseq_analysis projects/yeast_rnaseq_demo

Layer 05 05

外挂引擎层

真正重型的能力不是自研的，而是 vendored 进来的外部仓库：RFdiffusion、Evo2、Biomni、 LiteFold。Bio Studio 把它们组织进同一工作区里，让 AI 能够调度这些引擎。

repositories/active/RFdiffusion repositories/active/evo2 repositories/active/Biomni repositories/active/litefold
当前规模 约 5.9G，其中 RFdiffusion 3.3G，evo2 2.6G
结论 仓库的“能力”很多来自外部发动机，Bio Studio 做的是编排和使用语境。

执行回路

AI 在这里不是“帮你看代码”，而是被设计成能沿着完整研究回路走。

这个仓库的关键，不在于某个单独脚本，而在于 agent 可以从请求开始，一路穿过协议、技能、 MCP、项目工作区和报告输出，最后把产物落回可追踪的目录。

Bio Studio 的 AI work loop

下面这条链路，解释了为什么它是工作台，而不是普通资料仓。

关键路径

真正让 Bio Studio 有辨识度的，不是“工具多”，而是路径被预设过。

1. 读协议 AI 先看操作约束，再决定如何动手，不是直接盲跑命令。
2. 选接口 能通过 skill 或 MCP 走的路径，会优先变成可重复调用的工具面。
3. 进项目 分析尽量落在 `projects/<name>`，而不是污染仓库根目录。
4. 产物落盘 报告、结果和日志写回项目目录或 docs，让后续 agent 有东西可继承。
5. 经验回写 踩坑会进入 `BEST_PRACTICES`，环境变更进入 `CHANGELOG` 和 `ENVIRONMENT`。

现状与技术债

它是活的工作台，不是打磨完毕的产品，因此会同时存在锋利和粗糙的地方。

这部分很重要。你如果把它当 polished product，会挑出很多结构问题； 但如果把它当 AI research runtime，它的很多“不整洁”恰恰来自真实工作沉淀。

已经成型的部分

  • AI-first 的操作语境很明确，协议层写得足够具体。
  • 项目隔离理念贯彻得比较一致。
  • 已有 3 个可工作的 MCP servers 和 9 个本地 skills。
  • Ebola RNA-seq / yeast demo / toy playground 提供了现实样本。

明显半成品区域

  • `bio-design-mcp` 和 `bio-lab-mcp` 目前只是空目录。
  • `tmp/` 与 `evo2-7b-hf/` 没形成稳定职责。
  • `tools/scripts/` 成熟度不均，有些更像 exploratory scripts。
  • `lib/` 某些 wrapper 仍然比较脆，偏 shell glue 风格。

当前仓库风险信号

  • 外部引擎仓库当前有 2 个 dirty working tree。
  • `.gitmodules` 只映射了 RFdiffusion，litefold/source 仍不一致。
  • 仓库混合了代码、数据、结果和第三方源码，治理成本高。
  • 这是一套强依赖本地环境状态的系统，不是零配置 clone-and-run。

入口与使用

如果你要向别人介绍这个仓库，最好的方式不是口头解释，而是让他沿着这条入口路径走一遍。

先理解定位，再看协议，再看验证项目，最后再去碰真实案例和外部引擎。

推荐阅读顺序

1. README.md 先拿到全局定位：这是 AI 驱动的生物工作区，而不是普通代码项目。
2. CLAUDE.md 理解 agent 在这里的职责、环境规则和工作纪律。
3. docs/BEST_PRACTICES.md 看真实踩坑和已沉淀的环境经验。
4. projects/test_env_validation/ 确认这套环境不是停留在纸面，而是能走通基本工具链。
5. projects/ai_design_playground/ 看一条轻量的 dry-lab pipeline 是怎么写出来的。
6. projects/test_rnaseq_analysis/ 最后再去看最完整的 showcase 项目和重型引擎接法。
