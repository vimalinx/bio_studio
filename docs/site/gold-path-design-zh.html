先把平台主线立起来

这套仓库已经不是散装脚本集合了，但它还不是一个真正可打透的 AI 生物设计平台。 最合理的下一步不是继续堆工具，而是让 AI 能把自然语言目标稳定地落成一个 project，自动选策略、生成多候选、做代理评估并留下可复盘结果。

平台不该绑死在酵母 酵母只应该是参考 profile，不是平台本体。
第一阶段目标 做出可信的代理设计闭环，不是直接宣称真实研发闭环。
主线缺失 现在缺的是任务解释、profile 选择、候选账本和标准落盘。

一句话判断

底座已经像个平台了，但你真正想证明它能干活的那条设计金路径，还没有被打透。

70 / 100 通用 AI 生物工作区底座成熟度
20-30 / 100 可打透的 AI 设计闭环成熟度
已经有统一 CLI、MCP、shared runtime、外部引擎桥接、稳定测试
还缺任务解释、profile contract、候选账本、评估排序、标准 project 产物
推荐方向保留平台通用性，用一个参考 profile 证明主线可工作
Section 01

现状判断

先把“平台底座”和“设计闭环”分开看，不然很容易高估当前阶段。

已经成立的部分

  • 有工作区级入口 scripts/project.py。
  • 有 projects/ 作为任务实例层。
  • 有 5 个 MCP server，能力面已经铺开。
  • 有 shared runtime 和 LiteFold bridge 这种平台化思路。
  • 稳定测试链已经跑通，最近本地结果是 86 passed。

还没成立的部分

  • 还没有从自然语言目标一路走到 project 产物的主线。
  • bio-design 现在更像点状工具封装，不是自动决策路径。
  • 设计层的 profile 还没有真正站稳，特别是宿主/构建策略这一层。
  • 还没有统一候选管理、排序与证据记录机制。

最关键的结论

你现在缺的不是“再多几个工具”，而是把 任务解释 -> profile 选择 -> 候选生成 -> 评估排序 -> 项目落盘 这根主线立起来。

Section 02

平台主干结构

平台保持通用，具体生物学差异下沉到 profile。先把骨架固定，后面才能扩展多任务。

Layer01

Task Interpreter

把自然语言目标转成结构化任务书，至少要明确任务类型、分子对象、候选宿主、输出粒度、联网策略、成功标准和风险偏好。

task_type molecule_type candidate_hosts success_criteria
作用 把模糊目标变成可复现的任务输入。
Layer02

Profile Registry

平台本身不绑死在酵母、E.coli 或某个任务上，差异全部进入 profile，例如表达宿主、分子类型、评分逻辑与依赖资产。

yeast_expression ecoli_expression peptide_design rnaseq_analysis
作用 让平台保持通用，让专业逻辑可插拔。
Layer03

Orchestrator

真正的 AI 主线。它负责读取任务书、选择 profile、创建 project、安排阶段执行、调用 MCP 和脚本、在失败时留下结构化原因。

project creation tool routing retry / fail provenance
现状 scripts/project.py 是好入口，但它还不是 agent 编排器。
Layer04

Candidate + Evaluation Ledger

平台不该只产出一个拍脑袋答案，而是要管理多候选、评分拆解、证据链接、风险说明和不确定性。

multiple candidates scoring evidence risk notes
作用 把“会生成”升级成“会做设计决策”。
Layer05

Project Materializer

每次运行都要把全过程沉淀到 projects/，而不是只停留在聊天窗口里。

design_brief.json profile_decision.json candidate_table.csv evaluation_report.md
作用 让每次任务可复盘、可比较、可继续开发。
Section 03

当前缺口与优先级

真正阻碍你前进的不是“少几个工具”，而是中间决策层和数据落盘层没有统一模型。

最缺的 5 块

  • 统一任务书 schema
  • profile contract
  • 真正的 orchestrator
  • candidate ledger + ranking layer
  • 标准 project 产物模型

为什么不是继续加工具

  • 工具越多，没有主线时只会更散。
  • 每次都靠 prompt 临场发挥，结果不可复现。
  • 没有候选账本，就永远是“给答案”，不是“做决策”。
任务书与输出模型P0
profile contractP1
参考 profile 打透P2
候选管理与评估排序P3
标准化项目落盘P4
Section 04

前三步开发顺序

不要先做“全自动大脑”，先把输入输出和 contract 固定，再去打通主线。

第一步

先定义任务书 schema 和标准产物，比如 design_brief.json、run_manifest.json、candidate_table.csv。

第二步

定义 profile contract，不要先做很多 profile。先让“平台通用、profile 专用”成为真实代码边界。

第三步

只打透一条参考金路径，让 orchestrator 真正跑通一遍：解释任务、选 profile、生成候选、评估排序、落盘。

Section 05

最小可行金路径

平台不需要一开始支持所有生物任务，但必须有一条能证明自己不是空壳的纵向样板。

用户看到的路径

  • 输入一句自然语言目标
  • AI 自动创建一个 design project
  • 自动解释任务并选 profile
  • 生成多个候选方案
  • 输出 CDS / mRNA / construct 草案
  • 做代理评估与排序
  • 把全过程落盘到 projects/

系统内部更合理的方式

就算对外输出是 DNA 或表达构建，内部也不应该一开始就在裸 DNA 空间里瞎搜。 更可信的方式是：

功能意图 -> 分子候选 -> 反推成 DNA / mRNA / construct 草案

也就是：输出粒度可以在 DNA 层，但内部优化层最好还是先站在功能和分子层。

金路径成功的标志

  • 同类自然语言任务能稳定落成结构化任务书
  • 系统能自动建 project 并记录 profile 选择原因
  • 系统输出多个候选，而不是单答案
  • 每个候选都有构建草案、评分拆解、风险和不确定性
  • 失败时能明确说自己卡在哪一层
Section 06

现实边界

你这台机器能做出一个很像样的本地原型，但第一阶段别把代理评估吹成真实研发闭环。

现在现实能做的

  • 自然语言任务解释
  • 自动 project 创建与编排
  • 联网查数据库、文献、模板信息
  • 生成 DNA / CDS / mRNA / 构建设计草案
  • 做中小规模结构或代理评估
  • 输出多候选排序与报告

短期别高估的部分

  • 不要把功能预测当真值
  • 不要做超大规模候选搜索
  • 不要一开始承诺真实湿实验成功
  • 不要把第一阶段包装成“自动研发闭环平台”

最准确的第一阶段说法

本地优先的 AI 辅助生物设计与代理评估工作区， 而不是已经完成真实验证的全自动生物研发平台。
